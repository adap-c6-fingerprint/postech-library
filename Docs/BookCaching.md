# 도서 표지와 검색 결과 캐시

2026-10-27에 `feat/#47-48-home-map-tabs`의 표지 재요청·반복 검색 실측을 바탕으로 구현했다. 구현 전 측정과 구현 후 검증을 구분한다. 실기기 개선 시간·요청 감소율은 아직 측정하지 않았다.

## 1. 공통 표지 캐시와 화면 표시

`Shared/BookCover/SharedImageLoader.swift`는 화면 수명과 별도로 완료 이미지와 진행 중 요청을 관리한다. UI에 의존하지 않는 제네릭이므로 같은 코드의 공유·취소·보관 동작을 macOS에서도 테스트할 수 있다.

- 완료 이미지는 URL을 키로 하는 `NSCache`에 보관한다. 비용 한도 32MiB, 개수 한도 100개를 초기값으로 사용한다. NSCache의 한도는 강제 메모리 상한이 아니며 메모리 압박으로 제거될 수 있다.
- 같은 URL이 로딩 중이면 새 요청 대신 대기자만 추가한다. 완료되면 모든 대기자에게 결과를 전달한다.
- 한 화면의 취소는 그 대기자만 해제한다. 마지막 대기자가 떠나면 250ms 유예 후 네트워크 작업을 취소한다. 유예 안에 재진입하면 기존 작업에 다시 참여한다.
- 성공한 이미지만 캐시한다. 실패·취소는 다음 방문에서 재시도할 수 있다.
- 완료한 요청의 ID를 확인해 이전 작업이 늦게 끝나도 같은 URL의 새 요청을 제거하지 않는다.

`BookCoverPipeline.swift`는 기존 `URLSession.shared`로 데이터를 받아 HTTP 성공과 이미지 변환을 확인한다. 실제 캐시 값은 `UIImage`이며, 비용은 CGImage의 행당 바이트 수 × 높이로 계산한다. 새로운 이미지 라이브러리는 추가하지 않았다.

`BookCoverView.swift`는 추천·검색·상세가 함께 쓰는 SwiftUI 뷰다. 처음 만들 때 완료 캐시를 동기적으로 확인해 따뜻한 재방문에서 로딩 표시로 시작하지 않게 했다. 화면 표시 상태는 다음과 같다.

| 상태 | 표시 |
| --- | --- |
| 완료 | 받은 표지 이미지 |
| 로딩 | ProgressView |
| 전송·HTTP·이미지 변환 실패 | 검색·상세에서 ‘다시 시도’ 버튼. 홈 카드는 상세에서 재시도 |
| URL 없음·이미지 미제공 | 책 아이콘과 ‘표지 없음’ |

기존 각 화면의 표지 크기·배경·모서리와 Book 도메인 모델은 재사용했다. 검색 행에서는 표지와 제목의 상세 이동 버튼을 분리해 재시도 버튼의 중첩을 피한다. 검색·상세의 표지 재시도는 VoiceOver에서도 사용할 수 있다.

### 표지 오류 분석과 처리 보완 — 2026-10-27

사용자가 Swift 검색 결과의 `Swift.`(ISBN 9781807783877)에서 오류 화면을 제공했다. 같은 POSTECH 공개 검색의 4libs 표지 주소를 브라우저로 두 번 열어도 이미지가 표시되지 않았다. 같은 서버의 대조 표지는 85×122 이미지로 열렸다. 해당 표지 제공 경로에서 이미지가 표시되지 않는 현상은 재현했지만, 기기의 실제 오류 코드·HTTP 상태와 서버 내부 원인은 아직 확인하지 못했다.

- 원인: 기존 로더는 주소 없음만 기본 표지로 처리하고, 빈 응답·HTTP 오류·이미지 변환 실패를 모두 같은 ‘표지 오류’로 표시했다. 화면 내 재시도와 원인을 구분할 진단 로그도 없었다.
- `BookCoverFailure`는 2xx 빈 본문·공백만 있는 본문·204·404·410을 미제공으로 분류한다. 이 정책은 이번 기기에서 특정 HTTP 상태를 측정했다는 뜻이 아니다.
- 403·429·5xx·전송 실패·비어 있지 않은 손상 이미지는 재시도 가능한 실패로 유지한다. Content-Type만으로 거부하지 않고 실제 UIImage 변환으로 이미지를 검증한다.
- 기존 모델을 `BookCoverModel<Image>`로 분리했다. 취소와 늦은 응답을 무시하고, 같은 URL을 다시 로드해도 성공 캐시는 공유한다. 미제공 결과는 이미지 메모리 캐시에 영구 저장하지 않는다.
- OSLog의 BookCover 카테고리는 정해진 reason, HTTP 상태 숫자, URLError 코드만 기록한다. URL·ISBN·헤더·본문·원본 오류 설명은 기록하지 않는다.
- 추천 저장 시 미제공 표지는 별도로 표시해 목록을 유지한다. 상세 내용과 저장 형식은 `RecommendationCaching.md`를 참고한다.

새 공급처를 연결하거나 공급처의 원본 표지를 복구한 작업은 아니다. 실제 기기에서 Swift 검색·표지 없음·오프라인 실패·재연결 후 표지 재시도를 확인해야 한다.

검증: API·키 없이 Foundation 핵심 **39개 테스트 / 6개 suite** 실행 통과. 기존 24개를 재사용하고 미제공·실패 분류, 재시도·취소, 추천 미제공 보존·회복, 구버전 저장본 호환 테스트 15개를 추가했다. 앱 전체 Swift 소스의 iOS 모듈 생성과 BookDetailTests 전체 Swift 6 타입 검사도 통과했다. UIKit 화면과 iOS 테스트의 실제 실행은 별도 확인이 필요하다.

## 2. 검색 조건별 결과 캐시

`Clients/Book/Cache/BookSearchResultCache.swift`는 `[Book]` 메타데이터를 60초 동안 최근 20개 검색어까지 메모리에 보관한다. 날짜 공급을 주입할 수 있어 실제로 60초를 기다리지 않고 만료를 검증한다. Mutex로 reducer의 읽기와 비동기 Effect의 쓰기를 보호한다.

- 앞뒤 공백을 제거한 검색어가 현재 캐시 키다. 현재 BookClient의 범위·정렬·페이지 등 다른 조건은 고정되어 있다. 이 값이 가변이 되면 키에도 포함해야 한다.
- 만료는 마지막 성공 저장 시점 기준이다. 읽는 것만으로 60초가 연장되지 않는다.
- 한도를 넘으면 가장 오래 사용하지 않은 검색어를 제거한다.
- 빈 결과 `[]`도 정상 성공 결과로 보관한다. 오류와 취소된 요청은 저장하지 않는다.
- 디스크에 저장하지 않아 앱 프로세스를 다시 시작하면 사라진다.

`BookSearchCacheClient.swift`는 기존 TCA DependencyKey 방식에 맞춘 주입 경계다. 앱은 공통 메모리 캐시를 사용하고, 기존 테스트는 기본적으로 캐시를 사용하지 않는다. 새 캐시 테스트에서만 독립 캐시를 주입해 테스트끼리 상태가 섞이지 않게 했다.

`BookSearchFeature.swift`는 기존 최근 검색어 저장·검색 취소 Effect를 재사용한다. 동작은 다음 순서다.

1. 로딩 중이거나 빈 검색어인지 검사한다.
2. 최근 검색어를 기록하고 유효한 캐시를 찾는다.
3. 캐시가 있으면 결과를 바로 넣고 Effect 없이 끝낸다. 목록을 비우거나 isLoading을 켜지 않는다.
4. 캐시가 없으면 기존 검색을 수행한다. 성공 응답에서 취소 여부를 확인한 뒤 **제출했던 검색어**로 저장한다. 검색 도중 바뀐 입력어에 저장하지 않는다.
5. 새로고침은 해당 검색어의 기존 캐시를 제거하고 새 요청을 수행한다.

`BookSearchView.swift`에 검색 결과 새로고침 버튼을 추가했다. 검색 결과 캐시는 표지 이미지와 별도이며, 상세 화면의 최신 정보 조회를 대체하지 않는다.

## 3. 제한된 사전 로딩

HomeView는 추천 목록의 현재 위치 다음 최대 2권의 표지 URL을 공통 파이프라인에 전달한다. 전체 추천·검색 결과를 미리 내려받지 않는다.

- 중복 URL은 제거하고, 진행 중이거나 완료된 URL은 일반 표시 요청과 공유한다.
- 추천 목록이 도착하거나 스크롤 위치가 바뀌면 대상 URL도 바뀐다.
- SwiftUI task 수명이 끝나면 해당 사전 로딩 대기자를 취소한다. 다른 화면의 대기자는 유지된다.
- 2개·250ms·32MiB·60초·20개는 초기 정책값이며 실기기에서 최적값을 확인한 결과가 아니다.
- 사전 로딩은 다음 표지를 준비한다. 처음 보는 표지의 외부 응답 지연 자체는 남는다.

## 검증 결과와 남은 확인

아래 항목은 초기 캐시 구현 당시 결과다. #71 통합 후에는 추천 캐시 20개와 검색 결과 캐시 4개, 총 24개 테스트 실행 및 앱 모듈·도서 테스트 타입 검사를 통과했다. 실제 iOS 실행·실기기 개선 측정은 아직 확인하지 않았다.

- 공통 로더 7개와 결과 캐시 4개, 총 **11개 테스트**를 macOS 검증용 SwiftPM harness에서 실행해 통과했다. 실제 네트워크 대신 제어 가능한 응답을 주입했다. UIKit 어댑터·화면·TCA feature 실행 검증과 구분한다.
- 비밀 설정을 제외한 사본에서 로컬의 기존 의존성 모듈을 이용해 앱 전체 Swift 소스의 iOS 모듈 생성과 BookDetailTests 전체 소스 타입 검사를 통과했다.
- 새 TCA feature 테스트 5개는 반복 검색·다른 검색어 후 복귀·만료·새로고침 실패·검색 중 입력 변경·취소를 다룬다. 타입 검사를 통과했지만 실행은 하지 못했다.
- `xcodebuild build-for-testing`은 기존 의존성 매크로의 SwiftSyntax 모듈 해석 실패로 완료하지 못했다. CoreSimulatorService도 연결되지 않아 iOS 테스트 실행과 화면 확인을 못 했다. 기존 IndoorRouteClient의 Sendable 변환 경고는 이번에 수정하지 않았다.
- 공개 표지 2개를 인증 없이 추가 조회하려 했으나 DNS 해석에 실패했다. 실패 시간은 서버 응답 지연이나 개선 성과로 사용하지 않는다. 기존 실기기 trace의 응답 대기 분석을 기준선으로 유지한다.
- 실제 키·Secrets.xcconfig는 읽지 않았다. 검증용 설정에는 가짜 값만 사용했다. 초기 검증 당시 인증 API 호출·실기기 앱 재설치·Git commit·push는 수행하지 않았다. 후속 통합에서는 사용자의 명시적 요청으로 로컬 커밋을 생성했다.

실기기 후속 비교는 같은 추천 목록에서 좌우 왕복 3회·탭 왕복 3회, `스위프트→스위프트→과학→스위프트` 순서로 수행한다. 캐시 유지 조건의 완료 표지에서 추가 서버 요청이 없는지, 만료 전 반복 검색의 client 호출이 생략되는지, 새로고침·만료 후 조회가 수행되는지 확인한다. 화면 표시 시간과 메모리 사용량도 함께 측정한다.
